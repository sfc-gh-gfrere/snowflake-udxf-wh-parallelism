2. UDF vs UDTF

Back to top

Same input rows. The difference is how rows are grouped before they reach Python and what shape comes back.

UDF: UDXF_NET_REVENUE
1 · Input rows (colour = store)
↓
2 · Arbitrary batches
Any rows, any store, any order (e.g. up to 10,000 rows a batch).
↓
3 · Python handler, once per batch
price * units * (1 - 0.10 * promo)
↓
4 · Scalar output
One value per input row, as a new column.
24 rows in → 24 values out
  • Stateless: each row is calculated on its own.
  • Batching is up to Snowflake: the code doesn't care which rows are together.
  • Output: 1 value per row.
UDTF: UDXF_STORE_ELASTICITY
1 · Input rows (colour = store)
↓
2 · PARTITION BY STORE_ID
Every row of a store lands together, in one handler.
↓
3 · Python handler, once per partition
fit log(units) ~ log(price) + promo
↓
4 · Tabular output
STOREELASTICITYPROMO_LIFT
10.870.20
21.240.19
30.610.21
40.980.20
24 rows in → 4 rows out (one per store), any columns you choose
  • Stateful input: the handler sees the whole store at once (a regression needs every row).
  • Grouping is up to you: the partition key decides what goes together.
  • Output: a table, with any number of rows and columns.
Rule of thumb: if the answer for a row only needs that row, use a UDF. If it needs a group of rows together (per store, per customer, per device), use a UDTF with PARTITION BY. It's the Snowflake equivalent of groupBy().applyInPandas().

3. How the warehouse runs it in parallel

Back to top

Each warehouse node has 8 CPUs, and each CPU runs one lane: a Python process that's already started (hot) and waiting. The same warehouse that reads the table feeds the data straight into those lanes. Data never leaves the warehouse to reach Python.

Warehouse
Workload
STORE_SALES: micro-partitions in storage
↓ each node reads its share of the table and serves it to its own lanes ↓

Takeaway: wh_dop = nodes × 8. Doubling the warehouse doubles the lanes, and your code doesn't change. A UDF can spread its batches over every lane. A UDTF keeps each partition whole on one lane, so it scales with the number of partitions: 1,000 stores is plenty to keep 64 lanes busy.

4. The railroad analogy

Back to top

The same picture as section 3, told as a railroad.

TrackA lane (one CPU). 8 tracks per node.
TrainYour Python code plus its runtime. The engine stays hot: it isn't rebuilt for every trip.
CargoThe data. Each car is one batch of rows.
Rail yardThe warehouse loads the cargo onto the trains itself, with no hand-off to another system.
Workload
Takeaway: a bigger warehouse builds more tracks and puts a hot train on each one. Your code is the train, so it doesn't change. UDF: any car can ride any train. UDTF: every car bound for the same destination (a store) must ride the same train, because that train needs all of the store's cargo to do its job.
